3. **设施：** 建造/拆除费用、占地/地形、容量/范围、科技、支持物种/配方、维护、负责人及自动生产的适用规则。
4. **物种：** 采购与计量单位、设施/容量、成长、基础食谱与特殊食谱、扣料时点、有效生产日、产出、缺料/水体/花源影响、待收和收取后去留。
5. **配方/食谱：** 执行入口和主体、完整投入/产出、每批/每单位/整场口径、周期、科技、AP/费用、开始/维护/收取时点及自动执行限制。
6. **研究：** 前置、样本、费用、研究台、有效工作日、手动与雇工成本、全量解锁目标；解锁表和各实体自身门槛双向核对。

8. **规则：** AP/日结、光照水肥、水体花源、库存与在制/待收、雇工共享额度与预算、委托/自动生产目标及保留量、市场/供货、土地/工具/存读档中与实体获取和使用相关的现行规则。

数据缺失统一区分：`known`（已证实）、`not_applicable`（不适用，给理由）、`unresolved`（待核实，给问题ID）。不要用0或空字符串表示未知；无来源/无用途要判断是合理终点、仅采购品、未接通还是调查遗漏。玩家名缺失时追踪实际UI名称映射，不按英文ID自行翻译。

## 五、必须核对的易错口径

- 水分/肥力是环境值；清水/腐殖土是仓库物品。说明每格/每株扣减与每次维护的恢复，特别核对多格树和成熟待收状态。
- 光照不能仅二分喜光/喜阴：记录目标、容差、偏离后的倍率。查看多格平均与补光的实际取值方法。
- 成长可能用100点代表一天；记录整数取整、倍率叠乘、阈值、下限和日结顺序。标称天数与缺水低肥下的实际天数不能混写。
- 首次成长、再生、普通批时、动物育成、有效生产日和研究有效工作日分别记录。暂停与恢复不可写成继续正常计日。
- 幼体与成体、单单位与整场、满容量参考值要分开。每天基础食物和周期特殊投入不能合为一个“每日消耗”。
- 完工/成熟不等于进仓；未收产物不能计入已经可出售/使用的库存。自动策略可能计在制/待收量，需说明它与可用库存的区别。
- `recipes[].living`与物种特殊食谱若属于同一执行过程，应映射到同一规范过程；不能虚构普通台式加工路径或重复统计产量。不同变体保留各自条件。
- 科技门槛可能在物品采购、作物、物种、设施、配方或食谱多个层次；列本过程的直接门槛和必要上游前置，不把其中一项当作全部条件。
- 花源一天份额、手采与蜂群竞争、授粉是否叠加、换水每日次数/实物污水、净化损耗和矿物来源须从实际实现确认。
- 自动生产保留量、手动消费、基础照料、装置燃料的约束不同；不要写成任何时候都不会消耗保留材料。
- 市集价格0、不能购买/出售、不可供货不是同一回事；供货量、品阶、资格、向上取整和报酬需按实际报价规则核对。
- 区分游戏当前内容、遗留描述和未实现设想。静态调查不能称为自然经营试玩或平衡验收。

## 六、结构化交付契约

在`docs/farming/encyclopedia/audit/`输出以下五个文件，中文说明统一UTF-8，JSON使用合法数值/null而非字符串伪装数字；确定性排序方便复核。

### 1. `catalog.json`

顶层包含：

- `audit_schema_version`；
- `baseline`：日期、实际HEAD、工作区是否脏及相关差异、入口/产品/存档版本、已读取关键文件的相对路径和SHA256；
- `entities`：全部实体，含`id`（如`crop:golden_wheat`、`resource:straw`、`diet:steel_sheep/base/grass_meal`）、`kind`、`source_id`、名称、标签、逐字段事实、关联过程/规则ID、覆盖状态；
- `processes`：全部规范过程；
- `rules`：跨实体规则及受影响实体，含公式、参数、条件、取整/边界、时点、玩家解释与证据；
- `source_mappings`：原始注册项/食谱/运行入口到规范实体及过程的映射，解释合并/拆分，保证注册项不失踪。

推荐字段事实采用统一对象：`{status, value, unit, basis, conditions, evidence, issue_id}`。`evidence`为证据数组，每项有`path`以及`json_pointer`，或`symbol`＋`line_start`/`line_end`；标注`verification`为静态核查、运行验证或推断。JSON Pointer的数组索引同时记录实体原始ID，避免源表重排后误定位。

每个过程至少有：

- 规范`id`、类型、名称、操作者/设施/物种与原始映射；
- `inputs`、`outputs`：类型化实体ID、数量或公式、单位、计量基准、扣/领时点及条件；
- `costs`：AP/元石及发生时点；`requirements`：科技、设施、环境、状态、容量等非消耗条件；
- `duration`：数值、自然/有效日类型、推进条件、暂停恢复、完成与收取时点；
- `effects`：环境/进度/容量等非库存变化；
- `evidence`、`verification`和未解决问题引用。

无物品产出的消费过程允许`outputs: []`。有变量数量时保存公式、参数来源和取整，不能伪造固定数值。初始赠予仅是一次性来源；出售/供货是终端用途，和加工用途分组。字段名可作必要扩展，但须在报告中说明并保持全量一致，不要因结构复杂省掉事实。

### 2. `report.md`

- 基线、调查方法、实际读取与运行的范围；
- 按作物、物种、建筑设施、材料物品、配方食谱、研究、资源点、规则组织的总目录，所有条目可定位；
- 全部实体的字段摘要和来源/用途表，可引用JSON中的更细证据，但不得只给数量汇总；
- **金穗麦与秸秆的完整玩家可读样例**，包含逐项数据、全部来源/用途、科技/设施与跳转目标ID；
- 跨系统材料的抽查结果、发现的问题和后续实现建议；区分事实与建议。

### 3. `coverage.json`

- 各注册表原始数量、实际ID清单、调查实体/过程数量、食谱和活体映射数量；
- 每个原始ID对应的实体/过程、必备字段状态、来源与用途覆盖、证据；
- 重复ID、悬空引用、反向关系不一致、漏字段、无来源/无用途、未核实项；
- 原始输入/输出每一项与正反索引的数量/条件对拍结果；
- 对运行代码额外生产/扣料入口的检查清单、文件/函数与对应过程；
- 所有排除项及理由；循环回流与研究前置环分别处理。

### 4. `issues.md`

每项有稳定问题ID、严重程度、受影响实体/字段、现象、配置与代码/文档证据、玩家影响、已知范围和建议核查方向。不能确认的问题保留，不编造结论。

特别列出：无法解释的无来源/无用途、源表与baked差异、解锁表与实际门槛冲突、同名/缺名、单位不明、设计与实现不一致。即使没有问题也写明检查范围和结论。

### 5. `audit_entities.py`

提供只读、可复跑的枚举与一致性检查工具，报告中给出实际运行命令及结果。至少核对当前输入签名、逐ID覆盖、唯一ID、引用完整、必备字段状态和过程正反关系。运行时读取现有数据及调查交付，不修改源表/baked/代码，不从自身报告反推“没有遗漏”。

运行时入口覆盖仍需人工追踪并留下证据；脚本仅验证配方完整不能宣称全部玩法消耗已覆盖。若输入在调查期间发生变化，重核受影响范围并更新签名，或明确报告快照范围，不能混用前后版本。
