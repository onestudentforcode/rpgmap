# P10.2 分区回放与补跑

经营回放以「配置×策略」划成八个独立分区：`ordinary/A`、`ordinary/B`、`seed/A`、`seed/B`、`material/A`、`material/B`、`compound/A`、`compound/B`，分别是普通田、育种、丰产与复合区的两种策略。

每条仍从正常初始状态连续经营120日。运行、组装、审计、篡改检查可以分开执行；一条运行失败不会取消其他尚未启动的选中路线。已经成功且源码一致的路线直接复用账本。

## 常用命令

```powershell
# 查看八个分区状态，不启动游戏、不写账本
.\test-p10-2.bat -Stage Plan

# 只运行缺失的复合B；如果已经成功，则只核对它的账本
.\test-p10-2.bat -Stage Run -Cases compound/B

# 修复后，只重新经营复合B，原B账本与日志先自动归档
.\test-p10-2.bat -Stage Run -Cases compound/B -Rerun

# 可选择多条；Cases使用一个逗号分隔的字符串
.\test-p10-2.bat -Stage Run -Cases compound/B,seed/A -Parallel 2

# 只组装复合A/B，不运行游戏
.\test-p10-2.bat -Stage Assemble -Cases compound/B

# 只重审复合配置；若组装内容过期，自动用当前A/B重新组装
.\test-p10-2.bat -Stage Audit -Cases compound/B

# 只运行复合配置的16类篡改检查，不运行游戏
.\test-p10-2.bat -Stage Probes -Cases compound/B

# 最终核对全部八条与所有门禁，复用原始回放
.\test-p10-2.bat -AuditExisting
```

这些显式`Stage`/`Cases`命令直接进入经营分区，不重复模型/UI等快速检查。需要快速回归时单独运行`test-p10-2.bat -SkipPlaytest`；无参数入口仍先快速回归、再全量经营验收。`-SkipPlaytest`不能与分区选择同时使用。

所有命令可加`-EvidenceRoot .art-work/p102-my-check`指定独立目录。默认仍为`.art-work/p102-playtest/business-v5`。`Run`只启动选中的缺失路线；失败、中断、过期或残留日志不会被默默覆盖，需要检查后显式指定`-Rerun`。该开关作用于所有选中分区，建议重跑时写清`-Cases`。

## 各阶段的通过范围

| Stage | 工作内容 | 必要输入 |
|---|---|---|
| Plan | 列出missing/running/interrupted/failed/incomplete/invalid/stale/ready及原因；过期时列出变化文件 | 已有目录，或空目录 |
| Run | 运行选中的120日路线，或复用成功账本；单条账目复核 | 仅新运行需要Godot |
| Assemble | 将所选配置的A/B组装为对照 | 同配置A/B均成功、源码与设置一致 |
| Audit | 组装并严格核对所选配置的A/B | 同配置A/B均可复用 |
| Probes | 复制复合配置账本，验证16类篡改被拒绝 | 复合A/B有效，组装与当前原始账本一致 |
| Accept | Run→Audit→Probes；`-AuditExisting`跳过Run | 全部所需输入 |

`-Cases compound/B`在Run阶段只经营B；在Audit/Assemble阶段选择的是「复合配置」这组对照，因此仍须有A账本，但不会重跑A。`ready`表示可以重审的终态，不等于已经通过完整阶段验收。

每次操作在`EvidenceRoot/.steps/<批次>/`保存步骤日志及`result.json`。局部检查始终标记`acceptance_complete: false`；只有`Accept`选择全部八条并通过四组完整审计与篡改检查，才输出全量通过。单条检查允许未覆盖的产业配方，最终A/B严格审计仍要求原有完整产业门禁，不会降低标准。

重跑前，选中路线及其三个进程日志移入`EvidenceRoot/.history/<配置>/<策略>/<批次>/`，其他路线保持原样。进程PID和启动时间共同防止重复启动，分区锁防止两个调度器同时写同一份账本；运行中的路线不能被归档。中断或失败的账本保留供排查。

## 出错后重跑什么

| 改动或失败 | 处理 |
|---|---|
| 审计脚本、汇总表或日志处理出错 | 修正后执行Audit、Probes或独立报告工具，复用经营账本 |
| 单条进程失败或中断，源码未变 | 只对失败分区执行Run＋Rerun，再重审该配置 |
| 一条经营完成但审计失败 | 先查审计日志；调度器不会因审计失败自动再玩120日 |
| 清单内的经营策略、生产规则或数据变动 | 旧分区标为stale，列出变化文件；重跑受影响分区后再组装 |
| 共享生产逻辑或两条策略共同使用的操作器变动 | 所有引用它的分区失效，可能仍需八条都重跑 |

当前依赖以原始源码清单为准，保守地按整文件比较；不会自动判断“只改了某个分支，所以另一条一定没受影响”。需要进一步减少这类失效时，应先把策略与纯验收断言拆成独立文件，再为各分区记录准确依赖。不会修改旧清单哈希或混用不同版本A/B来节省时间。

本次没有将120日拆成四段30日。后段依赖存档、随机状态、研究、工资、操作器游标及前段账本，仅加载一个游戏存档不足以复原整条自动经营过程。现阶段优先使用八分区和独立审计步骤；时间段续跑应另做完整操作器检查点设计。

P10.2原验收记录`phase102-validation.json`保持为当时提交的历史证据，本次调度改动不重写该记录来冒充当时版本。游戏脚本和经营规则未改，原八条回放仍可重审。
