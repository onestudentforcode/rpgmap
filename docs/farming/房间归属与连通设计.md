# 房间归属与连通设计

> 2026-10-18，用户要求先落地本改动，再推进P10.4。
> 分层测试依据：`fad3a0c43d1cac524ac3400c2d7373f8c25e66bc`。

## 1. 明确的归属决定边界

房间由玩家框选/涂抹的地格集合与稳定ID确定。四邻接只验证同一ID内部连通，不以全地图地板洪泛决定归属。不同房间可以紧贴、使用同类地板，既不合并也不共享承载量。

物理房间归属、设施服务范围、三级系统关联是三套信息：服务可以重叠，房间可以关联，均不改变物理地格归属。一个物理地格最多一个归属，也可以未划区；同一设施的完整占地必须在同一个房间内才能计入配套。

## 2. 编辑行为

- 铺地板、开垦仅改变地面，不自动建立、扩展或合并房间。
- 农业使用“农业区与地板→划定新田块”；点击选择/取消耕地，确认创建。已有田块可编辑边界或解除划区。
- 畜牧继续沿用P10.3显式功能区，不因新农业机制创建第二套动物房间。
- 创建/编辑免费，但要求合法地权、合格地面、唯一地格、内部四邻接且不抢占他人归属。
- 不能以边界切开现存多格作物；种植也不能横跨两个田块或一半田块一半未划区。
- 添加邻接地格必须明确选择目标房间。自动吸附、自动合并、自动拆分均不提供。
- 编辑后不连通则拒绝；首版合并/拆分通过明确解除与重新划区完成，未加入自动迁移设施、动物的复杂命令。
- 解除农业划区保留真实作物、地面及历史生长贡献，只影响后续房间资格；不会把剩余地格转交邻居。
- 铺面拆改与归属独立。田块地板失效会暂停房间收益，但ID保留，修复原地板后可恢复；不能把旧农业归属地格直接划入畜牧，须先编辑/解除其归属。

## 3. 当前交付

农业保存`world.rooms.fields`（uid/name/cells）及`next_field_uid`；普通铺面、植物奖励与随机种子仍留原节。未划区耕地仍能种植、生长、正常收获，但没有整区房间奖励。

区域查询只遍历登记成员，不吸收旁边的空耕地。P10.2全占地覆盖、实际贡献、首次成熟与随机舍入规则保留；未声明的桥接地格不再稀释既有房间资格。界面显示田块名称/ID，并用不同颜色区分紧贴的田块。

新增API：`preview_field`、`create_field`、`edit_field`、`rename_field`、`erase_field`、`field_at`、`footprint_allowed`。Codec验证稳定ID、唯一坐标、连通、地权/地形、跨界作物及农业/畜牧重叠；合法失效配置仍可保存。

本改动使用schema22，新档开发，旧schema17～21明确拒绝且保留文件。P10.4在同一未发行的开发schema22继续扩展；没有为该中间开发格式承诺迁移。

旧测试夹具必须显式划田，禁止为照顾旧测试在运行时保留自动归属回退。历史经营文件不改；后续新的经营操作器需要实际执行划区。

## 4. 分层验证与证据

- 模型：`run_room_boundaries.gd`覆盖紧贴、桥接、外部新耕地、重复/断连/跨界、预览无副作用、JSON往返、合法暂停与修复、畜牧归属等。
- 既有回归：P10.2模型229项、P10.3模型550项通过；P10.2夹具由隐式连片改为显式登记，不再断言自动合并。
- 界面：`p87_scene.gd --check-only`通过，农业划区工具与现有输入路径接入；主观试玩未代签。
- 模块短场景：`run_room_boundary_playtest.gd`固定夹具，两个紧贴田块，一片全覆盖、一片无资格，真实推进3日并实际领取一次，18项通过。
- 收据审计：`audit_room_boundaries.py`验证两个ID保持独立、六条真实生长收据的房间资格、一次领取与库存差额相符；不依赖120日回放。

证据：`.art-work/p104-tests/boundary*.log`及`.art-work/p104-boundary/scenario.json`。夹具供料已明确标记为规则场景，不作为经营盈利证据。仅豁免已知Windows根证书环境警告，首轮默认user日志不可写已通过显式项目内`--log-file`解决。
