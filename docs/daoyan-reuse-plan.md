# 地图系统复用 daoyan — 工作流提案与问题清单

> 状态：待确认。本文档不依赖 daoyan 代码（按约定暂未读取），
> E 组接口问题在允许读项目后第一时间摸清。

## 0. 目标理解（请确认是否准确）

1. rpgmap 这套「网格 tile 地图 + 行走精灵 + 交互点」内核，作为 daoyan 地图方案的
   **新基础**，同时替代两条旧路线：函数实时生成（随机）、生图大图 + 热点。
2. 复用形态一：**星露谷式城镇**——多个城镇共用同一内核，单镇 = 多张功能地图 +
   特殊交互点，镇与镇之间靠数据/皮肤变化，代码零改动。
3. 复用形态二：**野外场景**——自身不承载战斗逻辑，只负责触发战斗。
4. 地图改为「**确定性、生成一次、永久复用**」的工作流产物：不再随机，
   美术素材可以按图定制与回填。
5. 现demo的「西西弗百货」命名只是玩法参考，属占位文案，后续统一改名（纯数据修改）。

旧方案为何不合适（一句话备忘）：AI 大图是**一次性**美术（改一处 = 重出整图、
碰撞/遮挡/可行走都靠热点硬贴）；tile 方案里一张 32×32 图块被复用千万次，
碰撞、Y-sort 遮挡、交互锚点全部由数据保证。

## 1. 工作流提案：四阶段（核心 = 把「生成」从运行时挪到构建期）

```
A 地图源数据 ──► B 烘焙 bake ──► C 运行时只加载 ◄── D 美术回填
   (git, 唯一事实源)   (显式, 产物进 git)    (永不生成)     (按 manifest)
```

### 阶段 A：地图源数据（唯一事实源，纯文本进 git）

- ASCII 字符画：地形 / 物件 / 门 / 出生点（rpgmap 已验证的方式）
- 每图元数据：id、名称、尺寸、传送表（双向）、交互点注册表
  （id → 类型 + 参数 + 对话 id）
- **城镇 = 主题包**：`字符 → 图块` 映射表、调色板、物件皮肤、对话内容；
  同一布局可换皮，同一定位可换布局——「内核复用，细节变化」就落在这层

### 阶段 B：烘焙（显式构建步骤，headless Godot 脚本）

- 校验：图例全覆盖、传送表双向对称、出生点/交互引用存在、尺寸一致
- 产物：TileSet + 各地图场景存为 `maps/baked/*.tscn`（提交 git）
- **同时产出资产清单 manifest**：该图用到哪些图块/物件/动画帧——
  这就是 ComfyUI 美术生产的「采购单」，美术按单生产，不多不少
- 只在源数据变化时重跑；同一张地图不需要生成第二次

### 阶段 C：运行时（只加载，不构建）

- MapHost：加载烘焙场景 → 挂 YSort 容器 → 相机边界 → 玩家/门户/交互/对话
  （rpgmap 现有内核直接演化，删掉运行时 build 路径）
- 野外战斗触发 = 一种**带类型的交互点**（`battle_trigger`），只负责把
  encounter_id 等参数抛给战斗系统，地图本身不关心战斗

### 阶段 D：美术回填

- ComfyUI 按 manifest 出图 → 切图/QC 工具处理 → 覆盖 `assets/` 贴图 → **不重烘**
- 只有布局/图例变化才需要重新烘焙

## 2. 两个场景的落位

| 场景 | 复用什么 | 场景特有 |
|------|----------|----------|
| 城镇 | MapHost + 门户图 + 交互/对话 + Y-sort | 功能地图数据包、主题皮肤、交互点类型（商店/存档/任务…） |
| 野外 | 同一套地图系统 | `battle_trigger` 交互点类型 + 战斗入口/返回接口对接 |

## 3. 待拍板问题（附推荐默认值，可只回「按推荐」）

### A. 接入方式（最阻塞，先定）

- **A1 宿主方向**：把 rpgmap 内核移植进 `daoyan/godot`，还是以 rpgmap 为基底
  长成正式项目？
  推荐：移植进 daoyan（复用主体是它；rpgmap 保留为玩法沙盒）。
- **A2 旧方案去留**：新地图系统落地后，旧的实时生成/生图热点地图是立即全量替换，
  还是新旧并存逐步迁？第一批迁移哪些内容？
- **A3 命名**：正式设定名叫什么？（现 demo 文案全部数据驱动，改名 = 改数据文件）

### B. 工作流形态

- **B1 编辑界面**：ASCII 进 git（推荐起步，程序员友好、可 diff、成本最低）/
  Godot 编辑器手铺（美术友好）/ Tiled 外部工具？地图由谁维护（只有你，还是会有美术协作）？
  推荐：先 ASCII，工作流跑通后如需美术协作再补编辑器导入。
- **B2 烘焙产物**：烘焙出的 .tscn 提交 git（推荐）/ 启动时从源数据现算？
- **B3 城镇结构**：单镇典型几张图？屏幕级小地图 + 边缘走出切换（星露谷式），
  还是大图滚动 + 门传送（现 MVP 方式）？
  推荐：先延续大图 + 门，工作流不用改；边缘切换后续作为门户的一种特例加。

### C. 内容与美术

- **C1 第一垂直切片**：选哪张图？（某城镇的广场？还是先做野外触发验证？）
- **C2 规格**：tile 维持 32×32、视口 640×360（daoyan 的 UI 基线是否兼容）？
- **C3 地形清单**：第一张图需要哪几种地形（草地/泥土/路/水/悬崖…）？
  要不要 autotile 过渡变体（每种地形 47 变体，美术成本差一个量级）？
  推荐：切片图先不做 autotile，直边过渡。
- **C4 特殊交互点类型**：第一张图要哪几种（商店 / 存档点 / 宝箱 / 任务 NPC /
  传送点 / 调查物件…）？每种的行为定义一句话即可。
- **C5 美术工序**：ComfyUI 出图后的切图、色板清理、QC 由谁做？
  是否把现有 `gen_placeholder_assets.py` 扩成「切图 + QC」工具？
- **C6 持久化**：一次性交互标记（已开宝箱/已对话）接 daoyan 现有存档系统，
  还是先做内存级（切图不丢、重开游戏重置）？

### D. 野外战斗场景

- **D1 触发形态**：走进区域即触发 / 走到点位按键触发 / 可见标记？一次性还是可重复？
- **D2 战斗接口**：进战斗要传什么（encounter_id？队伍快照？剧情前文？）；
  战斗结束回野外要恢复什么（位置/状态/战后标记）？
- **D3 野外规格**：规模、地形，与城镇共用 tileset 还是独立野外主题？

### E. 允许读 daoyan 后要摸清的接口（移植设计的前置）

1. 场景管理与启动流程：autoload、现有地图节点挂接方式、`daoyan/godot/` 结构
2. 对话/叙事系统：我们的 DialogueUI 是**替换**还是**桥接**进现有系统
3. 战斗系统的进入/退出接口（对应 D2）
4. 存档/状态系统（对应 C6）
5. 输入映射、UI 主题、分辨率基线是否冲突；有无现成玩家角色与行走动画资产
